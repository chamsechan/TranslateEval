**译研评测台：当前设计与功能的系统性评价**

**总体判断**

架构和领域建模总体合理，适合可信环境中的单机翻译实验管理；正常参数、单 Worker 下的主要流程已经可用。不可变数据版本、预测完整性核验、评价配置修订、逐句原始分保存，以及任务与统计查询分离，都值得保留。当前无需改成微服务，也不需要为扩展性重写整个框架。

但不能认定“各项设计均达到预期”或“功能完全正常”。一方面，参数边界、并发领取、并发提交和跨模块有效评分口径仍有可复现缺陷；另一方面，系统能够计算和追溯分数，并不证明这些分数已经能够可靠衡量小语种翻译质量。作为实验记录工具，当前成熟度明显高于作为经过校准的质量裁决系统。

**当前已验证的问题**

P1 表示应先修复，会破坏结果可信度或造成重复评分；P2 表示输入、状态或常见异常操作存在功能缺口。方法学建议单列，不把已明确约定的策略误写为实现错误。

**1. P1：参数校验与评分落库之间缺少一致的数值约束。**

位置：[BLEU 参数及返回值](../backend/app/evaluators/bleu.py#L25)、[LLM 参数](../backend/app/evaluators/llm.py#L153)、[评分落库](../backend/app/queue.py#L352)。

通过 API 创建 `smooth_method=floor, smooth_value=100` 的 BLEU 配置返回 200。真实 Worker 执行仓库 6 句演示预测后，把 **160.6857、561.2222** 等分值保存为成功结果，任务显示 `completed/6`。结果查询依据 0–100 范围排除这两条，返回 **有效评分 4/6、覆盖率 66.7%、聚合为空**。用户会同时看到任务成功与结果缺分，而且“重试失败项”无法覆盖这些状态为 completed 的异常分数。

`smooth_value="bad"` 同样可保存，执行时才报永久错误。LLM 的 `temperature="nan"`、`timeout_seconds="inf"` 和负 `max_tokens` 可通过目前的转换式校验；其中 NaN 温度实际在请求 JSON 序列化时失败，尚未向 Mock 服务发送请求。相反，清空并发/超时/重试字段发送 null 会返回明确 400，**未发现此前怀疑的 500 问题**。

建议：为每类评价器定义完整的配置 schema，校验类型、有限性和参数关联；不要仅靠 `int/float/bool` 转换。评分结果在统一落库入口校验有限数值和声明范围，非法值记失败并保留原因，不能静默夹到 100。BLEU 的 1e-9 满分误差处理与真正越界需要分别对待。

验收：错误配置保存时得到明确 4xx；任何成功评分必须满足其尺度约束；队列成功数、详情有效评分数、整体 sentence_mean / corpus BLEU 的样本数一致。逐语种聚合保留其子集大小，macro_sentence_mean 的 sample_count 保留语种数。

证据：[metrics-evidence.json](system-review-2026-09-07/metrics-evidence.json)、[可运行探针](system-review-2026-09-07/metrics-probe.py)。

**2. P1：“严格可比”与统计页对“有效评分”的定义不一致。**

位置：[comparison_checks](../backend/app/queries.py#L88)、[scored_item_condition](../backend/app/queries.py#L147)。

比较逻辑检查 completed 状态、ScoreResult 记录及来源，未校验实际分值是否落在有效范围。上述两个只有 **4/6 有效评分**的任务，比较仍返回 `strictly_comparable=true`、无警告。旧版本存在的“忽略实际 Prompt 来源”已修复，本次是另一条异常分值路径。

建议：列表、详情、聚合和比较统一使用有效评分条件；完整覆盖必须按实际数据集样本与有效分数交集判断。

验收：上述案例不得标为严格可比；完整且来源相同的合法结果保持可比。证据同上。

**3. P1：第二个 Worker 会将仍在运行的任务当作中断任务恢复，造成重复评分。**

位置：[启动恢复](../backend/app/worker.py#L21)、[恢复查询](../backend/app/queue.py#L135)、[领取与处理](../backend/app/queue.py#L589)。

隔离复现中，让第一个 Worker 的评分请求保持在途，再执行第二个 Worker 启动时相同的恢复与处理逻辑：**6 个样本被调用 12 次，保存 12 条 ScoreResult，最终任务仍显示 completed/6**。恢复没有核查任务归属或租约，领取也没有原子条件更新。单机定位允许只支持一个 Worker，但当前程序未强制这一边界；重复执行启动脚本也可能遇到它。

建议：维持单 Worker 时先增加进程/数据库独占锁并给出重复启动错误；需要多个 Worker 时再实现原子领取、owner/lease 和仅回收过期租约。心跳文件不能充当任务所有权锁。

验收：重复启动被拒绝或安全共享队列，活跃任务不被回收；既有成功结果不会因第二实例重复计费。

证据：[queue_repro.py](system-review-2026-09-07/queue_repro.py)、[queue_evidence.json](system-review-2026-09-07/queue_evidence.json)。

**4. P2：同一导入报告的提交只保证顺序重复调用，不保证并发幂等。**

位置：[commit_submission](../backend/app/api.py#L499)、[commit_submission_import](../backend/app/importers.py#L501)。

用两个 Session 先读同一 validated 报告，再交错完成提交，生成 **2 个不同 submission 和 2 个 task**。这模拟两个请求均在首次提交完成前读到旧状态；不是声称正常浏览器点击一次就会重复。现有幂等测试覆盖的是顺序重试，缺少这种交错。

建议：在同一事务里原子认领导入报告，或给导入报告与提交关系加唯一约束；竞争者读取已产生的结果。前端禁用按钮只能减少触发，不能替代后端保证。

验收：两个同时提交同一报告的请求只能生成一组提交/任务，并返回同一结果或明确冲突。证据：[import-evidence.json](system-review-2026-09-07/import-evidence.json)、[import_probe.py](system-review-2026-09-07/import_probe.py)。

**5. P2：无效语种格式仍能通过“严格导入”。**

位置：[DatasetSampleInput](../backend/app/schemas.py#L26)。

`source_language` 只做去首尾空白、小写化和长度校验。实际把 `!!!`、`123`、`en zh`、`中文` 四个值作为语种成功导入并登记，报告 `valid=true`。空白语种已有测试拦截，但这不等于语种代码格式校验。无效分类会污染按语种宏平均和识别统计，也与 README 的“无效语种代码阻止整批写入”不符。

建议：明确支持的语种标签格式，允许格式合法的未知代码并保留显示回退，不必把范围硬编码为当前种子语言；源语种与预测语种使用一致的规范化规则。

验收：上述无效格式在核验阶段失败，原有 `de`、`th` 等代码和明确支持的带地区/文字标签仍可导入。证据同上。

**6. P2：源文与参考译文同时改变时，版本差异漏报参考译文变化。**

位置：[版本差异分类](../backend/app/importers.py#L234)、[界面计数标签](../frontend/src/pages/DatasetsPage.tsx#L135)。

同一 ID 同时修改源文和 GT，实际报告 `source_changed=1, reference_changed=0`，明细也只有 source_changed。原因是互斥的 `if/elif`。当前界面把两个字段分别命名为“源文变化”和“参考译文变化”，因此会让用户误以为 GT 没变。

建议：分别统计两个维度并说明可重叠，或者增加“源文与参考译文均变化”的类别和明细。验收：双重修改在预览中明确可见，不丢失任一变更事实。证据同上。

**7. P2：逐句“评分中”状态没有由 Worker 实际维护。**

位置：[请求执行与结果写入](../backend/app/queue.py#L661)、[逐句状态筛选](../frontend/src/pages/ResultsPage.tsx#L192)。

Worker 将 item 从 queued 直接转为 completed/failed/cancelled，没有在发起请求时设置 running。在途请求仍显示等待评分，前端提供的“评分中”筛选无法反映实际请求。它不改变最终分数，但削弱排查卡住请求和观察真实并发的能力。

建议：发起调用时维护在途状态与开始时间，并在取消/恢复/终态逻辑中一致处理；或去掉尚未实现的状态承诺。验收：人为阻塞的请求可在逐句列表中筛到，恢复后不永久残留 running。证据见队列探针。

**8. P2：取消整个任务遇到后端错误时，前端没有显示可操作的错误。**

位置：[TaskCard 取消确认回调](../frontend/src/components/TaskCard.tsx#L21)。

本次 Chromium 将 `POST /api/tasks/{id}/cancel` 模拟为带 detail 的 500，确认对话框停留，页面不显示服务端错误，出现未处理 Promise 错误。数据集取消和重试已有 catch，整任务取消分支未保持一致。

建议：捕获确认回调异常，显示服务端 detail，保留重试入口；不能提前把界面改成已取消。验收：模拟 4xx/5xx/断网均显示明确失败并能再次操作。

证据：[取消故障注入记录](system-review-2026-09-07/frontend/evidence-cancel-error.json)、[浏览器截图](system-review-2026-09-07/frontend/cancel-error.png)。注入错误用于验证反馈路径，不表示正常取消接口总会返回 500。

**9. P2：目录导入的错误数据集元信息不能在编辑表单修正。**

位置：[草稿数据集项合并](../backend/app/import_api.py#L178)、[目录 key 禁用](../frontend/src/components/SubmissionImportEditor.tsx#L19)、[不可增删的列表](../frontend/src/components/SubmissionImportEditor.tsx#L137)。

目录实际为 `flores-demo/predictions.jsonl`，仅 result_info.json 把 key 写成 `wrong-key`。prepare 保留错误项并追加正确项，而目录导入的 key 均不可编辑，错误项版本不可选，列表也没有删除按钮。浏览器无法完成修正，必须改源文件或绕到 API；直接用 API 删除错误项后，同一份暂存预测即可核验通过，说明问题在元信息编辑流程。

建议：区分实际预测目录和 manifest 多余项，允许删除无文件对应的项，或提供明确的目录到数据集映射。验收：只写错 JSON 元信息时，用户能够在导入编辑页修正并重新核验，无需修改合法预测文件。

证据：[错误元信息的 API 核验](system-review-2026-09-07/frontend/evidence-bad-manifest-api.json)、[无法修正的界面](system-review-2026-09-07/frontend/bad-manifest.png)。完整正常流程和浏览器复现说明见 [前端证据](system-review-2026-09-07/frontend/README.md)。

**评测设计中需要重新明确的选择**

**“分数达到阈值”不宜无条件等同于“翻译正确”。** 当前实现与 README 的公式相符：微平均通过率为 `passed/全部样本`，宏平均按所有语种等权；失败和未评分计未通过，平均分只看有效评分。这套规则适合同时衡量质量与评分完成率，但它会让评分服务故障降低被测翻译的“准确率”。建议保留全量通过率，并明确命名；需要比较模型本身质量时，另给有效评分上的条件通过率和覆盖率，而不是悄悄更换现有分母。

BLEU 主要反映参考译文匹配程度，阈值无法自动判断语义正确。本次默认配置的两个反例是：

| 参考译文 | 候选译文 | sentence BLEU | 默认阈值 20 的界面结论 |
| --- | --- | ---: | --- |
| 我支持这个决定。 | 我不支持这个决定。 | 75.0624 | 正确 |
| 请关闭窗户。 | 请把窗关上。 | 11.4787 | 未通过 |

这证明“BLEU ≥ 20”不能在所有样本上等价于正确翻译，不是 SacreBLEU 算错，也不据此推断它在真实语料上的总体误判率。建议 BLEU 报告突出 corpus BLEU 与逐语种结果，将阈值指标称为“达标率/通过率”；如保留“准确率”，应注明代理指标及校准条件。

**LLM Judge 尚缺少质量校准闭环。** [默认 Prompt](../backend/app/evaluators/llm.py#L21)提供准确性、完整性、流畅性方向，却没有分数锚点、错误等级或分语种验证证据。框架没有证明选用的 judge 对各小语种都足够可靠。建议先建立覆盖各语种、否定、数字、专名、遗漏和流畅改写的人工复核集，检查 judge 与人工的一致性、阈值误差以及多次评分波动，再决定某个阈值是否可作为发布标准。待评文本应清楚界定为数据，并将诱导评分的候选文本纳入验证集；本次没有用真实 judge 测量此项。

**缓存策略符合 README，但不适合作为严格配置实验的隐含默认。** 当前键包含源语种、源文、GT、译文和模型名，故意忽略 Prompt、Base URL 与参数。它对历史内容复用有效，实际来源也能追溯；但用新 Prompt 或另一服务重复评测时，若不开强制评分，结果可能完全来自旧配置。建议保留已有复用模式，同时提供包含完整评分配置指纹的严格模式；更换 Prompt/服务/参数的实验默认使用严格模式或明确提醒预计复用范围。不能把跨配置缓存命中当作验证新配置成功。

**语种识别的分母需要在 API 和界面说清楚。** 6 条样本只有 1 条提供语种、且正确时，当前返回 accuracy=100%、coverage=16.7%；德语共 2 条仅覆盖 1 条，recall 仍是 100%。这是在已提供标签样本上计算的条件指标。若意图评价端到端识别，总体应为 1/6，德语 recall 应为 1/2。建议同时返回 `accuracy_on_covered` 和 `accuracy_overall`，逐语种召回明确是否把缺失输出计入；不要在未声明条件时使用常规 recall 标签。证据见 metrics-evidence。

**“严格可比”只证明比较前提，不证明差异显著。** 数据版本、来源和样本集合一致是必要条件，但当前结果仍是点估计，缺少置信区间、配对比较和语言分层不确定性。SacreBLEU 官方已提供配对 bootstrap 和近似随机化检验，可以作为后续实现基础；其中文 tokenizer 与 signature 也支持当前框架选择。[SacreBLEU 官方说明](https://github.com/mjpost/sacrebleu)

**可维护性、规模与运维评价**

模块化单体仍合适。下一步可顺着职责拆分已经超过 1,200 行的 api.py 和约 800 行的 queue.py，把任务状态、调度执行、结果判定分开；本次“有效评分”定义分叉说明共享领域规则比单纯减少行数更重要。API 大量手工 dict 与前端手写类型也增加契约漂移风险，优先补核心响应模型和统一状态类型。

有明确的规模改进：列表采用批量关系加载、服务端过滤/排序/分页，已有 SQL 次数回归测试。剩余代价在于每个评分响应都会 `_refresh_progress`，再次扫描当前任务的所有项并提交；N 个互不重复样本的累计扫描量近似 O(N²)。数据导入、待评项读取和比较还会把对应记录全部载入内存。逐响应持久化提升了恢复能力，但可以用短时间窗口提交、增量计数及周期校准保留这种优势。不能仅以 6 句 demo 或查询次数固定就认定大规模性能达标。

本次无网络假评分器的 SQLite 基准如下。耗时是本机观察值，包含 ORM、队列处理和落库，不是网络 LLM 的吞吐预测；O(N²) 指累计扫描工作量，不表示这些小规模实测时间已经严格平方增长。

| 不同样本数 | 耗时 | SQL 语句数 | 全任务状态计数次数 |
| ---: | ---: | ---: | ---: |
| 200 | 1.216 秒 | 2,234 | 201 |
| 1,000 | 6.406 秒 | 11,050 | 1,001 |
| 3,000 | 22.523 秒 | 33,090 | 3,001 |

基准中心跳最大年龄为 2.514 秒，低于 API 的 6 秒断线阈值，**未复现心跳误报**。取消后中断再恢复也通过：原有 1 条成功评分保留，其余 5 条取消，父任务为 partial_cancelled。

另有低优先级状态语义不一致：所有项都失败时 evaluator 是 failed，父数据集和任务仍会标 partial_failed；submission.status 也不是同一提交下所有任务状态的完整聚合。当前前端主要依赖任务层级状态，但后续扩展 API 时应统一这些含义。

暂存文件在上传中间文件和 staging 失败时有清理，但已成功暂存、已提交及部分准备失败目录没有统一保留期限/回收机制；长期运行需要可观测的占用和安全清理命令。`setup.sh` 的 pip 与 npm install 也没有形成统一的锁定安装流程。0001 迁移直接调用当前 ORM metadata，历史迁移不是固定 schema；本次空库迁移和现有 Prompt 升级测试通过，仍建议以后把新迁移写成固定操作并持续验证旧库升级。

部署脚本监听 0.0.0.0，而应用没有用户身份与权限隔离，并允许服务器路径导入；API Key 明文保存这一点 README 已公开说明。对于可信单机可以作为明确的运行前提；若要变成共享服务，需要先给出真实访问控制和资源边界。当前范围无需强行引入复杂权限系统，但不能把“单机”理解为“只监听本机”。

**已修复并在当前版本得到验证的旧问题**

运行中重试导致遗留 queued、取消后继续发送等待中的请求、等待慢请求才落库、比较忽略缓存来源、旧活动任务被固定长度列表挤出、预测暂存内容变化仍能提交、仅当前页分数排序、全失败语种消失等，均已有对应的当前回归测试并通过。测试还覆盖空角色 Prompt、非数值 LLM 分数拒绝、Prompt 删除引用保护、设置历史快照、结果/数据集版本导航，以及多列服务端排序。不能继续用旧报告的“19 项测试通过”评价当前保障水平。
