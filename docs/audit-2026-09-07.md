审计日期：2026-09-07。对象：当前工作区，包括原有未提交修改。本次新增审计文档与证据，未修改业务代码。

## 结论与适用范围

项目的产品定位、领域模型和页面分工总体合理，已经能完成单机翻译评测的主要流程。数据版本不可变、推理信息留档、评分结果保留原值、评价器修订与 Prompt 版本分离，这些设计值得保留。

目前的主要短板是任务状态的一致性、结果比较的可信度、异常后的恢复路径，以及历史数据变多后的可用性。建议先修复这些问题，再扩展评价器和美化页面。以当前规模，继续采用模块化单体、API 与 Worker 分进程的方案合理。

| 维度 | 判断 | 优先改进方向 |
| --- | --- | --- |
| 易用性 | 熟悉协议的开发者能够使用；首次使用和错误恢复仍依赖文档 | 导入模板、失败后原地重试、明确加载状态、历史检索 |
| 功能可靠性 | BLEU 基本流程通过；队列并发操作与缓存比较存在已复现缺陷 | 重试状态机、取消语义、实际评分来源检查 |
| 模块划分 | 领域实体合理，应用层职责开始集中 | 拆分路由、任务状态、调度、统计查询，统一接口契约 |
| 页面设计 | 导航、卡片和配色统一；工作台的信息优先级仍可调整 | 修复对比度与溢出，突出核心评测指标，降低 JSON 暴露 |
| 扩展能力 | 适合小规模单机试用；缺少对大数据与多客户端的保障 | 服务端分页、批量查询、增量推送、暂存生命周期 |

## 应优先修复的问题

P1：优先处理，涉及错误任务状态、错误比较结论、取消后继续发起请求或关键记录不可见。P2：下一轮修复，涉及常见使用障碍、边界输入与可扩展性。

### 1. P1：运行中重试失败项，会留下无法执行的待评分项【已复现】

位置：[queue.py](../backend/app/queue.py#L191)、[完成状态计算](../backend/app/queue.py#L694)、[TaskCard.tsx](../frontend/src/components/TaskCard.tsx#L72)。

任务仍在运行时，只要已累计失败项，前端就显示“重试失败项”。后端没有限制任务必须处于终态，会把失败项及评价器任务重新改为 `queued`。但当前 Worker 使用的是启动时读取的样本列表，不会重新取回已处理过的失败项；结束时仅检查失败数，没有检查剩余 `queued` 项。

复现：101 条样本、并发 1；第 1 条失败，第一批落库后，在第 101 条执行时触发重试。最终评价器状态为 `completed`，实际为 **100 条 completed、1 条 queued**。Worker 只领取 `queued` 状态的评价器任务，因此这 1 条不会再执行。

建议：短期同时在前后端禁止运行中重试，后端对非法状态返回明确冲突错误；终态判定必须检查待执行项。后续需要运行中重试时，将其设计为独立重试批次或明确的调度事件。回归用例应覆盖“部分失败 → 运行中点击重试 → 最终所有项都有一致终态”。

### 2. P1：取消只在整批边界生效，尚未发出的请求仍会继续执行【已复现】

位置：[queue.py](../backend/app/queue.py#L604)。

每批至少包含 100 条候选记录。代码一次为整批创建协程，等待信号量后直接发请求；取消检查位于整批 `gather` 前后。已取消任务中仍在等待并发名额的请求不会停止。

复现：6 条样本、并发 1，第一次调用时取消任务，最终仍调用评价器 **6 次**。这超过了提示中“已经发出的请求可能继续”的范围，可能产生额外等待与评分消耗。

整批结果也在 `gather` 返回后才持久化；一个慢请求会延迟该批全部进度更新，Worker 中断后该批尚未落库的成功结果需要重新执行。

建议：取得并发名额后、每次重试前检查取消状态；停止调度尚未发送的请求。对已完成响应使用单独写入流程按小批或短时间间隔提交，并保留在途请求结果的既定缓存策略。

### 3. P1：“严格同口径”没有核查缓存的实际评分来源【已复现】

位置：[compare_results](../backend/app/api.py#L580)、[LLM 缓存查找](../backend/app/queue.py#L272)。

比较接口只检查任务声明的数据版本、评价器修订和 Prompt 版本。缓存按产品既定策略忽略 Prompt 和 Base URL，因此声明的版本不一定是实际评分版本。

复现：先使用 Prompt A 评分；再创建两个声明使用 Prompt B 的任务，一个允许缓存、另一个强制评分。第一个任务 6 条全部来自 A，第二个任务 6 条全部来自 B，接口仍返回 **`strictly_comparable=true`**。

建议：保留现有宽松缓存策略，但把“请求配置一致”和“实际评分来源一致”分别判断、分别显示；实际来源混合时给出明确说明。还应检查成功样本集合和覆盖率，避免不同样本子集的均值被误解为严格公平比较。对比页可以提供基于共同成功样本的统计。

### 4. P1：实时推送会使历史任务从列表中消失【已复现】

位置：[TasksPage.tsx](../frontend/src/pages/TasksPage.tsx#L13)、[任务列表及 SSE](../backend/app/api.py#L443)、[ResultsPage.tsx](../frontend/src/pages/ResultsPage.tsx#L71)。

任务页先请求最新 100 条，SSE 只发送最新 50 条，前端收到事件后直接覆盖整个列表。过滤发生在截取之后，较早但仍在运行的任务也可能不在“活动”筛选里。

复现：同一数据库中 REST 返回 **60 条**，SSE 返回 **50 条**，最早任务在前者存在、后者不存在。结果列表最多读取 200 个父任务，模型记录默认只取 100 条，均没有继续向后查询的分页入口。

建议：统一服务端分页、总数和筛选参数；活动任务独立查询。SSE 按任务 ID 更新已有记录或通知缓存失效，不以固定长度快照覆盖历史列表。提交后利用返回的任务 ID 定位新任务，防止快速完成的任务立即从默认“活动”页消失。

### 5. P2：核验通过的推理结果在提交时没有完整性复核【已复现，需暂存文件发生变化】

位置：[commit_submission_import](../backend/app/importers.py#L490)。

数据集提交会重新校验内容哈希，但推理结果提交只重新解析 JSONL；未比较预测内容摘要，也未重新检查完整 ID 集合。因此这属于本地暂存文件被修改、替换等情况下的缺陷，不是正常浏览器操作必然发生的问题。

复现：6 条预测核验通过后，将暂存文件改为仅保留 1 条合法预测，仍可提交并完成；报告原来显示 6 条，最终任务仅有 1 条且覆盖率显示 **100%**。

建议：核验阶段保存每个预测文件的稳定内容摘要和样本集合信息，提交阶段重新核对；覆盖率的总量还应与所绑定的数据集版本相互校验。

### 6. P2：多选评价器实际串行执行，与界面承诺不符【代码确认】

位置：[worker_loop](../backend/app/queue.py#L724)、[SubmitPage.tsx](../frontend/src/pages/SubmitPage.tsx#L91)、README 功能说明。

Worker 每次只领取一个评价器任务，并等待其全部执行完毕后才领取下一个。并发仅存在于单个评价器任务内部。大批 LLM 评分会阻塞后续 BLEU 或其他评价器，界面却描述为“可多选并行评测”。

建议：短期准确描述为“多选后依次执行，各评价器内部并发”；若实现跨评价器并行，补充全局与各服务并发额度、公平调度和原子领取。当前启动恢复会直接重置所有 running/preprocessing 任务，不能简单多启动几个 Worker 来弥补。

## 易用性与结果分析

### 7. P2：非法输入能被保存，或返回无帮助的服务器错误【已复现】

位置：[上传端点](../backend/app/api.py#L255)、[ZIP 解压](../backend/app/importers.py#L39)、[Prompt schema](../backend/app/schemas.py#L122)、[模板渲染](../backend/app/evaluators/llm.py#L98)、[BLEU 配置验证](../backend/app/evaluators/bleu.py#L24)。

实测包括：

- 文件名为 `.zip` 但内容不是 ZIP：返回 **500 Internal Server Error**，未说明压缩包损坏。
- Prompt 中直接写常见 JSON 示例 `{"score":8,"reason":"ok"}`：保存返回 200，渲染时才抛 `ValueError`；界面未提示字面花括号必须转义。
- BLEU tokenizer 填写不存在的值、默认阈值填写 1234：仍能创建配置。
- 保存的 `max_retries=0`，打开编辑窗口变为 **3**，不改该字段直接保存就会改变重试策略。原因是 [SettingsPage.tsx:54](../frontend/src/pages/SettingsPage.tsx#L54) 用了 `|| 3`。

建议：把模板试渲染、变量检查、tokenizer 枚举及评价器对应的阈值范围提前到保存阶段；对 ZIP 错误返回可操作的 4xx 提示；合法零值使用 `??` 保留。保存按钮应具备提交中状态，避免反复创建修订。

连接测试只调用 `/models`，不能证明实际评分请求可执行。应区分“服务可达”“模型可见”和“评分试跑通过”；对于没有标准模型列表的服务，不应直接宣称模型可用。

### 8. P2：失败状态与空数据状态混淆，导入错误恢复路径不完整【已复现／代码确认】

位置：[DatasetsPage.tsx](../frontend/src/pages/DatasetsPage.tsx#L21)、[导入 Modal](../frontend/src/pages/DatasetsPage.tsx#L74)、[DashboardPage.tsx](../frontend/src/pages/DashboardPage.tsx#L18)、[ModelsPage.tsx](../frontend/src/pages/ModelsPage.tsx#L12)、[SettingsPage.tsx](../frontend/src/pages/SettingsPage.tsx#L34)。

实测将数据集 API 置为 503，页面显示“还没有数据集”，同时存在未捕获的 Promise 错误。首页请求失败会一直保留骨架屏；模型和设置页也缺少完整的初始请求错误处理。

数据集核验失败后，输入区域被替换，Modal 的 footer 为 null，除了右上角关闭按钮没有“修改路径／重新核验”入口。浏览器实测核验失败对话框内仅剩关闭按钮。

建议：统一 loading / success-empty / error / stale 状态；错误提示附重试操作。导入失败时保留输入和文件信息，提供原地重新选择与再次核验。公共 API 层还需把 Pydantic 数组形式的错误转换为字段提示，而不是直接传入 `Error`。

### 9. P2：分数排序只作用于当前 50 条，结果详情也不会自动刷新【代码确认】

位置：[结果分页加载](../frontend/src/pages/ResultsPage.tsx#L119)、[表格分数 sorter](../frontend/src/pages/ResultsPage.tsx#L222)、[后端固定按 ID 排序](../backend/app/api.py#L667)、[结果页重试](../frontend/src/pages/ResultsPage.tsx#L177)。

逐句结果使用服务端分页，但排序函数只处理当前 `items`。超过 50 条时，点击升序并不能找到整个任务中最低分的样本。

详情允许查看未完成任务，但上下文、统计和逐句列表不订阅进度；重试只修改前端局部状态，没有重新拉取评分和统计，可能持续展示重试前结果。切换任务时还应统一重置页码与筛选，避免沿用前一个任务的第 N 页。

建议：排序、搜索、状态、语种与分数区间全部在服务端组合查询，并在分页前执行。活动详情按事件或受控轮询刷新，终态停止；重试成功后失效相关查询。将阈值、筛选和页码放入 URL，便于分享和返回恢复。

### 10. P2：研究分析需要的部分信息已存储，但没有完整页面入口【代码确认，产品优化】

- 数据集版本页只能看数量和哈希；后端已有样本查询，前端未接入。导入 diff 保存了变化 ID，但界面只展示计数，缺少源文和参考译文的前后对照。
- 模型记录的副标题承诺“解码信息永久记录”，数据库也保留了 `result_info`；当前列表接口和页面没有运行详情，用户看不到 decoding、precision、code_revision 等复现参数。
- 语种识别接口返回混淆矩阵和逐语种结果，页面只显示“混淆矩阵数据已保留”，无法查看矩阵。
- `threshold_summary` 只从成功项生成 `by_language`。某语种全部失败时，会从图表和语种筛选中消失；总覆盖率虽存在，但缺少逐语种覆盖、失败和取消数。
- 缺少结果导出、报告导出以及按同一批推理结果更换评价器的便捷入口；这会使反复实验依赖再次导入。

建议优先补数据预览、运行详情、逐语种覆盖表和 CSV/JSON 导出，再扩展更复杂的图表。首次使用可从数据版本直接生成带正确哈希的 `result_info.json` 模板，并提供演示包下载和明确的操作步骤。

## 页面设计审计

### 11. P2：结果页存在实际对比度问题和窄窗口溢出【已复现】

位置：[styles.css](../frontend/src/styles.css#L9)、[深色结果卡片样式](../frontend/src/styles.css#L86)、[阈值布局](../frontend/src/pages/ResultsPage.tsx#L206)。

1440 像素窗口中，深色结果卡片上的“微平均分／宏平均分／宏准确率／评分覆盖率”标题实际计算颜色是 **`rgba(0, 0, 0, 0.45)`**，没有应用预期浅色。当前 Ant Design 统计组件规则的选择器优先级覆盖了项目样式，因此标题难以辨认。

1024 × 768 窗口中，结果页实际宽度达到 **1149 像素**，阈值输入框伸出卡片；`body` 固定最小宽度 1120，加上固定栅格和 Slider 最小宽度造成溢出。这也影响笔记本分屏和页面放大使用。

建议使用组件语义化样式或局部主题确保深色卡片文本颜色；补充 1024/1280 等断点，使侧栏自动收起，阈值区域在窄屏转为独立一行。表格采用容器内滚动，长 ID 和 URL 可换行或复制。

对宏平均、微平均和阈值准确率增加简短解释，明确后者是评分阈值下的通过比例。逐语种图表建议配套可排序的数据表；语种多时提供缩放或滚动。图标按钮补可访问名称，可点击数据集卡片补键盘入口。

## 模块划分与扩展性

### 12. P2：SSE 每个客户端每秒重复查询完整任务树【已测量】

位置：[task_dict](../backend/app/api.py#L150)、[task_events](../backend/app/api.py#L455)。

序列化逐层访问 ORM 关系，没有批量预加载；每个 SSE 客户端独立每秒查询最新 50 条完整任务树，即使最后不推送，查询与 JSON 构建仍已发生。该查询还同步执行在 async 路由的事件循环内。

在复用同一数据集／提交、每任务一个评价器的隔离数据中，**一次 50 条 SSE 快照触发 107 条 SQL**。这是实测查询数，不是生产吞吐量结论；更复杂任务树和更多客户端需要进一步负载测试。

建议先用批量关系加载或专用列表查询减少 SQL，再将推送改为按变更版本更新或共享快照。阈值汇总当前也会把所有成功评分及样本文本实体加载进 Python，宜采用数据库分组聚合，只读取计算需要的字段。

### 13. P2：导入暂存缺少生命周期，容易持续占用磁盘【代码确认】

位置：[stage_source](../backend/app/importers.py#L49)、[报告持久化](../backend/app/importers.py#L106)。

每次核验都复制目录或解压 ZIP；成功提交、核验失败和放弃操作均没有清理已展开的目录。上传临时 ZIP 会删除，但展开后的目录继续保留。目录复制与 ZIP 解压也没有总量、文件数或展开大小限制。

建议定义核验报告和暂存文件的保留期限、可见空间占用与清理入口；提交后保留需要的审计信息即可。为导入限制大小，并避免源目录包含暂存目标时发生递归复制。

### 当前模块设计：边界合理，但职责集中【设计建议】

后端 `api.py` 878 行，混合导入、配置、任务、查询、序列化和 SSE；`queue.py` 886 行，混合任务创建、状态转移、调度、重试、缓存、落库、BLEU 聚合和统计接口。前端页面文件同时维护请求状态、表单、数据转换及较长 JSX，重复的错误处理已经出现差异。

建议分步调整为：

```text
backend/app/
  api/                 # datasets、evaluations、settings、results 路由
  services/            # 导入、提交、重试等业务操作及事务边界
  jobs/                # 状态转移、调度、执行、恢复
  queries/             # 列表、比较、统计、分页
  evaluators/          # 保留现有评价器接口与实现
  models.py            # 当前规模可继续保留

frontend/src/
  features/datasets/
  features/evaluations/ # 提交、队列、结果，共享领域类型
  features/settings/
  shared/api/          # 统一错误、请求取消、类型契约
  shared/components/   # 加载、错误、空状态及通用组件
```

路由应专注输入输出，事务由业务操作统一管理，统计不依赖 Worker 内部实现。给状态定义明确的枚举和允许转移关系，集中计算父子任务状态。建立显式的请求／响应模型，减少手写字典、TypeScript 接口和 `Record<string, unknown>` 的重复维护；无需为了拆文件引入额外服务或复杂仓储抽象。

跨 Worker 并行之前需要任务领取原子性、归属／租约以及按失效租约恢复。保留单 Worker 也应防止重复启动，并说明支持边界。

### 前端体积与测试保障【已测量／设计建议】

本次构建中 `antd-vendor` 约 **1.19 MB**、`charts-vendor` 约 **1.09 MB**，gzip 后分别约 381 KB、364 KB。浏览器访问没有图表的总览页时也请求了 charts 分块，说明当前手动分块依赖关系没有达到预期的图表按需加载效果。

建议检查构建依赖图，修正共享分块关系并验证总览页网络请求；随后按需注册图表组件。实际响应压缩需结合服务部署验证，不能把构建给出的 gzip 估算当作已启用传输压缩。

19 项现有测试覆盖基本评分、取消前置状态、重启状态恢复、缓存和提交事务，但未覆盖本次发现的运行中重试、取消后待发送请求、实际来源比较以及前端分页等行为。优先添加这些有业务意义的回归用例，再补 3 条浏览器流程：首次使用完整流程、导入失败修正、历史结果筛选与分页。把后端测试和前端构建接入持续集成。

## 建议实施顺序与验收标准

| 阶段 | 工作 | 验收标准 |
| --- | --- | --- |
| 第一轮：可靠性 | 修复运行中重试、取消、比较判定、任务截断；补提交完整性检查 | 不出现 completed 任务残留 queued 项；取消后不再发起未发送调用；来源不同不能被标为严格同口径；历史与活动任务均可查到 |
| 第二轮：日常使用 | 修复输入验证、加载错误、导入恢复、排序、结果刷新、零值回填、对比度和溢出 | 非法输入有明确提示；断网不会显示成无数据；低分排序跨全部页正确；1024 窗口主要操作可用 |
| 第三轮：研究工作流 | 数据预览、版本 diff、运行详情、逐语种覆盖、导出、模板生成 | 用户从界面即可核查语料、复现参数和评分来源，并导出本次分析 |
| 第四轮：可维护与规模 | 随功能拆分职责，优化查询与 SSE，完善暂存清理和调度 | 查询数不再随每条关系逐层放大；多客户端共享变更查询；磁盘占用可观测、可清理；构建资源按页面加载 |

现有的明文密钥保存与宽松缓存策略在 README 中已明确，本报告不将这两个约定本身作为缺陷。若使用范围从可信本机扩大到多人共享，应重新确认访问边界：当前脚本监听 `0.0.0.0`，API 没有应用级鉴权，服务器路径导入与配置修改也没有用户隔离。
