# TranslateEval 多数据集、多语种、多版本页面评价

评价日期：2026-09-07。只检查当前前端，不修改产品代码。

结论：现有的版本绑定、语言分页、明细筛选和逐句下钻可以保留；数据集目录、版本管理、复杂任务展示和逐语种模型对比需要调整。40 个语言本身不会使页面失效，主要问题是查找效率、长页面和比较能力。

## 范围与方法

使用当前构建的 Vite preview、Chromium，在 1440×1000 和 1024×900 两种视口模拟 API。假设 **12/20 个数据集、每集 20 个版本、40 个语种，每语种 10,000 句**；任务队列另假设每页 20 个任务、每任务 12 个数据集、每集 2 个评价器；结果列表假设共 1,200 条评测记录。这些数据集数、版本数及任务形态都是用来暴露页面问题的测试假设，不是用户已确认的数量。

`400000` 是模拟响应中的总数，样本接口只构造一页 20 条，结果明细只构造一页 50 条。此实验验证分页请求、DOM 规模和操作流程，**不能证明真实 40 万行数据库查询、导入或评分的性能**。所有请求均被本地拦截，没有接触真实模型服务。

证据：[`frontend-verification.json`](./frontend-verification.json)、可重跑脚本 [`frontend-scale.mjs`](./frontend-scale.mjs)。执行方式：在 `frontend/` 下运行 `npm run preview -- --port 4177`，另一个终端在仓库根目录运行 `node docs/scale-review-2026-09-07/frontend-scale.mjs`。脚本含本环境 Playwright 与 Chromium 的绝对路径，其他环境需修改这两处。

当前“各语种结果”表的分页与图表折叠是实测存在的改进。不能把旧版未分页的问题继续作为当前缺陷。

## 有限结论与优先级

1. **先改任务展示与版本管理**：这是实际操作路径中最突出的长页面问题。20 版本查看旧版本需要经过约 7 屏内容；一个含 12 数据集、2 评价器的任务本身已超过一屏。
2. **增加多语种对比矩阵**：在每语种 600–10000 句不等时，总体分数不能替代按语种检查。当前已经同时展示 micro/macro，但对比页仍需进入每个模型详情逐一查看语言。
3. **补充数据集目录检索和明细审阅工具**：固定 20/50 行能控制单次 DOM 数量；是否能支撑真实数据库查询由后端实测决定。上万页并不是可行的人工评估流程，需要筛选、抽查与导出。
4. **保留已有的分页、版本上下文和下钻**：这些能力适用于新增规模，不必重写。图表是次要视图，可以随后优化。

本次没有复现新的页面崩溃；最终浏览器记录没有 JavaScript 页面错误。12 条对比数据的“严格可比”由模拟响应固定提供，本次不验证后端可比性判定，也不把模拟评分当作真实评测结果。
