# TranslateEval 后端查询规模验证

2026-09-07。仅增加评估材料，未修改业务代码。

## 结论

40 语种本身没有造成查询错误：分页、单语种筛选、精确样本 ID、统计覆盖和两结果比较均返回 200，并通过关键计数断言。单语种 1 万句的评分列表约 0.19 秒，精确 ID 约 0.08 秒。

全版本 40 万句的日常读取已明显变慢：评分首屏约 4 秒，最深页约 11 秒；仅两条结果的列表约 5–6 秒。两个完整评分任务比较约 40.5–40.8 秒，独立请求进程的 RSS 总峰值约 2492 MiB（2.43 GiB；请求前约 74 MiB）。这不适合直接作为当前规模上界的日常交互体验。

执行 SQLite `ANALYZE` 后，关键慢查询和比较内存没有得到实质改善。维护查询统计仍有价值，但本专项的主要问题是每次重新遍历样本、排序方式和全量 ORM 加载。

## 方法与边界

- 单独 `/tmp` SQLite，当前 SQLAlchemy 模型建表，WAL 开启。使用 Core 每批 4000 行造数，绕过正式导入和 Worker；造数耗时不能作为产品导入或评分吞吐。
- 每库 **1 个数据集、2 个完整版本、40 语种、2 个模型提交、2 个完成的评分任务**。分别每版 24,000 / 400,000 句，即每语种 600 / 10,000 句。两版本均保留完整样本副本；本测试不验证版本差异的语义。
- 大库共 80 万样本、80 万预测、80 万评分明细、80 万独立 ScoreResult。源码约 150 个 ASCII 字符，参考和译文约 80 个汉字，reason 约 80 个汉字，并在 raw_response 中保留相同评语。评分为合法的合成 0–10 分，无真实 LLM。
- 追加历史时共有 6 个完整任务、240 万 EvaluationItem、80 万 ScoreResult；4 个新历史任务复用首个模型的预测和评分，模拟缓存命中。
- 每个 API case 在**新的子进程**中使用 FastAPI TestClient 调用真实 router，覆盖依赖、SQL、ORM 和响应序列化，90 秒超时。计时不含模块导入和造数，不含网络传输；RSS 是该子进程总峰值，不能当作额外净内存。未清空操作系统文件缓存，非独占机器或并发用户压力测试，数值是本机参考而非 SLA。
- 环境：4 CPU、约 23.4 GiB RAM，Linux aarch64，Python 3.12.3、SQLAlchemy 2.0.52、SQLite 3.45.1。没有实测多个大数据集同时存在、12 个结果比较或更多版本的极限。

## 原因与代码位置

1. **结果列表汇总依赖样本联表扫描。** [queries.py:178](../../backend/app/queries.py#L178) 的 `result_summary_statement` 连接样本、预测、明细和评分后聚合。默认列表先分页，再汇总当前页任务；每条列表记录仍有该任务全版本的样本成本。

2. **均分 / 通过率排序先汇总全部匹配任务。** [api.py:771](../../backend/app/api.py#L771) 把筛选后的全部任务 ID 传入聚合，随后排序分页；[api.py:794](../../backend/app/api.py#L794) 再汇总当前页一次。范围由筛选后的任务集合决定；默认不加筛选时包含所有结果任务。SQL 使用索引查各任务对应评分，并非无条件顺序扫描整张 ScoreResult 表，但扫描工作量随匹配任务的样本总量增长。

3. **默认主键排序也创建临时排序结构。** [queries.py:31](../../backend/app/queries.py#L31) 的通用 `table_order` 无条件增加 `column IS NULL`。主键本身非空，仍会在[评分明细查询](../../backend/app/api.py#L918)的 `ORDER BY` 中出现。24k 未维护和 400k ANALYZE 后的 EXPLAIN 都显示 `USE TEMP B-TREE FOR ORDER BY`。明细还选择完整 ScoreResult ORM（包括未在列表输出的 raw_response），最深页的 OFFSET 使临时排序更昂贵。计数查询也保留了全量外连接。

4. **比较把全部评分对象装入 Python。** [queries.py:96](../../backend/app/queries.py#L96) 对每个任务 `select(Prediction.sample_id, ScoreResult).all()`，包含 reason 和 raw_response，并为每个任务保留样本到来源信息的字典。[api.py:807](../../backend/app/api.py#L807) 先逐任务统计，再执行此来源检查。统计维护后索引计划改善，40 万行的 ORM 解码、对象创建和字典开销仍保留，比较实测没有变快或省内存。

5. **版本语言计数每次重新扫描样本。** [queries.py:158](../../backend/app/queries.py#L158) 为版本按语种分组计数；[api.py:383](../../backend/app/api.py#L383) 数据集列表统计所有数据集的最新版本，[api.py:408](../../backend/app/api.py#L408) 版本列表统计该集所有版本。本次只有 1 个数据集 / 2 版本，已经约 0.58 / 1.05 秒；更多数据集和版本的成本尚未实测。

## 优先改进建议

- 为结果列表持久化或缓存有效样本数、均分、默认阈值通过数及每语种汇总；在评分进度或重试改变时精确失效。均分排序直接使用任务级汇总，不在每次翻页时联表计算所有明细。
- 比较来源和样本集合改为 SQL 差异检查或分批流式读取窄字段，避免加载完整 ScoreResult 和每个任务全量 ORM。
- 非空主键使用直接索引排序；明细选择页面所需字段，按筛选情况简化计数，深页采用游标分页或其他有界定位方式。单语种筛选和精确 ID 已证明现有组合索引有价值。
- 不可变版本的每语种样本数在导入完成时保存；版本和数据集列表读取汇总数据。
- 保留 `ANALYZE` / 数据库维护机制；本专项结果表明它不能代替上述查询改动。仅更换数据库也不会消除全量 ORM 加载与重复汇总的应用层成本。
