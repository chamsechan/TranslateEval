# TranslateEval：多语言规模下的导入与 Worker 实测

本次验证了 40 个语种 × 每语种 600 / 10,000 条样本，即每版本 24,000 / 400,000 条。真实数据导入、版本差异核验、预测导入与建立评测任务均成功；40 万条规模下已经出现较高内存、较长同步等待和可复现的数据库写锁超时。创建任务成功不表示整轮评分性能合格。

## 方法与边界

- 使用当前产品的 `validate_dataset_import`、`commit_dataset_import`、`validate_submission_import`、`commit_submission_import`、`create_evaluation_task`、`_joined_item_rows`、`_refresh_progress`，没有替换产品实现。
- 每项操作启动独立 Python 子进程。峰值 RSS 为该进程的 `resource.ru_maxrss`，包含约 62 MiB 应用基线；时间为本机一次运行的观测值，SQL 事件计数本身有少量开销，不是受控性能基准或部署容量承诺。
- 每个规模导入两个版本，第二版本仅修改 1% 的参考译文；随后对第一版本导入一份全覆盖预测，建立一个未执行的 BLEU 评价器任务。
- 源文均值约 163 字节、参考译文约 195 字节；每条源文与参考包含记录编号，缓存键互不重复。语言代码用于检验分组规模，合成源文为英文占位内容，未评估实际多语种翻译质量或长文本场景。
- 没有调用任何模型或外部 API，没有执行 40 万条逐项评分。Worker 仅测预处理和 3 次进度计数。
- 未测 HTTP 上传以及当前界面完整的 `prepare → validate → commit` 路径。界面的 `prepare_import` 还会全量解析一次样本。预测提交 API 将预测持久化与任务建立放进同一个事务，本次将二者拆为独立阶段测量。
- 临时数据和数据库均在 `/tmp/translateeval-scale-*`，执行结束后自动删除，未修改产品数据库与业务代码。

## 实测结果

| 操作 | 24,000 条耗时 | 24,000 条峰值 RSS | 400,000 条耗时 | 400,000 条峰值 RSS |
|---|---:|---:|---:|---:|
| 数据集核验 | 0.52 s | 95 MiB | 8.13 s | 563 MiB |
| 数据集提交 | 3.16 s | 104 MiB | 59.69 s | 625 MiB |
| 新版本差异核验 | 1.11 s | 154 MiB | 19.30 s | 1,484 MiB |
| 新版本提交 | 3.22 s | 104 MiB | 61.83 s | 626 MiB |
| 预测核验 | 0.41 s | 109 MiB | 6.91 s | 750 MiB |
| 预测提交 | 2.79 s | 101 MiB | 57.27 s | 673 MiB |
| 建立一个评价器任务 | 2.11 s | 72 MiB | 38.07 s | 149 MiB |
| Worker 全量加载待评项 | 1.47 s | 185 MiB | 23.48 s | 2,043 MiB |

版本差异计数正确：24,000 条中识别 240 条参考变化、23,760 条不变；400,000 条中识别 4,000 条参考变化、396,000 条不变。两个规模的差异详情都只保留前 200 条，因此此规模下完整差异审查还需要查询或导出能力。

`_refresh_progress + commit` 在全体待评状态下调用 3 次：

| 规模 | 第一次 | 第二次 | 第三次 |
|---|---:|---:|---:|
| 24,000 条 | 27.2 ms | 18.4 ms | 17.6 ms |
| 400,000 条 | 294.0 ms | 290.7 ms | 284.2 ms |

空历史评分缓存的检查：24,000 个键共 120 批，约 0.30 秒；400,000 条场景仅检查前 200 个键的一批，约 0.006 秒。两者都没有历史评分，不能代表大量历史缓存的查询性能。

## 关键设计问题

### 1. 每项完成后全量重计进度

`queue.py:384` 按整个评价器任务扫描状态计数和缓存命中计数，`queue.py:695` 在每个评分内容组完成后调用它，并提交事务。通常内容互不相同，则 N 条评分约触发 N 次全任务计数，进度维护总工作量接近 O(N²)。40 万条场景下一次调用已经约 0.29 秒，且位于异步评分主循环中的同步数据库路径。这里没有实测完整评分时长，不应将前述数值写成端到端吞吐。

建议通过批次增量更新计数、周期性校准、按批持久化进度来限制工作量，并给失败、取消、重试和缓存命中保持一致的计数语义。

### 2. Worker 全量装载和对象保留

`queue.py:244` 将 `EvaluationItem`、`Prediction`、`DatasetSample` 的整份 JOIN 结果 `.all()` 后再生成 `ScoreInput`。24,000 条对应 72,003 个驻留 ORM 对象，400,000 条对应 1,200,003 个，后者开始评分前已约 2 GiB。

评分过程中 `current_results` 保留整个任务的 `ScoreResult`，包含 `raw_response`；缓存字典也持有评分 ORM 对象。结束时 `_store_aggregates` 再次全量读取评分、样本和预测，因此预处理峰值是有限场景的观测值，不能作为完整 LLM 任务内存上限。

建议按数据库游标/主键范围分批加载，限制缓存和结果对象驻留量，最终统计采用可增量聚合的实现；多语种任务可以进一步按语种或分片调度。

### 3. 导入长事务确实阻挡其他写操作

尽管每 1,000 条执行一次 `flush`，导入仅在最后执行 `commit`。实测 40 万条提交约 60 秒，执行约 400,000 条插入 SQL，数据库写锁会持续覆盖大部分插入阶段。

在 40 万条第二版本提交期间，独立 SQLite 连接使用与产品相同的 30 秒等待上限，执行 `BEGIN IMMEDIATE`，**30.19 秒后得到 `database is locked`**。探针没有提交任何改动。这说明同时进行导入和评分持久化等写操作已存在可复现冲突；不代表所有并发请求都会失败，也没有测 HTTP 错误表现。

建议导入改为有进度、可恢复的后台作业，使用真正批量写入，缩短占用共享库的写事务；在保留版本发布原子性的前提下设计暂存到发布过程。若部署需要多人同时导入与评分，应一起评估数据库的并发写入方案。

### 4. 多版本与多轮推理会放大存储

40 万条测试中的数据库大小：

| 持久化状态 | SQLite 文件大小，十进制 MB |
|---|---:|
| 一个数据版本 | 341.6 MB |
| 两个数据版本 | 682.7 MB |
| 两版本与一份预测 | 924.4 MB |
| 再建立一个未执行的评价器任务 | 1,015.4 MB |

第二版本只改 1%，仍完整复制样本。以上还没有任何 `ScoreResult` 或 LLM 原始响应；应用保留的两份数据与一份预测暂存文件另占约 470 MB。测试工作目录约 1.96 GB 的总量同时包含额外的原始合成输入，不能全部算作应用持久化开销。

`stage_source` 创建的正常暂存目录没有自动清理路径。建议明确未提交草稿和已提交原文件的保留期限、归档与清理策略，提供存储用量；版本数量较多且差异较少时再考虑样本内容与版本成员关系去重。

### 5. 语种仍是统计维度，尚未成为操作单位

当前结果导入强制预测 ID 完整覆盖整个数据版本，不能直接导入某几个语种或按批追加预测。一个 `EvaluatorJob` 覆盖整个数据集，Worker 按顺序处理完整任务；无法按语种独立调度、取消或重试。多个大数据集排队时，先到的大任务会长时间占据单 Worker。

如果实际工作习惯是整版完整推理，这种约束能保证覆盖一致性；如果希望先评某几个语种、分阶段补齐结果，则应明确建模评测范围，并同步修改完整性与可比性判定。
