# Worker 与评价器优化验证

本次修改涵盖 `queue.py`、`worker.py` 和 `evaluators/`，没有调用真实模型。

## 实现

- 任务项使用 `INSERT … SELECT` 在数据库中批量生成，不把全部预测 ID 或任务项 ORM 放进 Python。
- Worker 按主键最多读取 512 条；只保留当前批次的输入、候选缓存与结果对象。历史缓存按完整内容键进行索引等值查询，每键取一个最新合法评分，不读取评分理由与原始响应。跨批次去重借助数据库，不保留整任务字典。
- 初始与终态各校准一次完整进度，评分完成后仅累计本批次的完成、失败和缓存增量。多个同时返回的结果合并提交；慢请求仍在运行时，已经返回的结果会及时持久化。
- 只有已经分配执行槽的请求组标为 `running`，等待执行的项保持 `queued`。取消后停止新分配，保留在途调用返回的评分原件；任务恢复会把中断的 `running` 项重新排队。
- CLI Worker 先取得数据库路径对应的操作系统独占锁，再恢复中断任务。重复启动明确拒绝，不会错误恢复另一个活跃 Worker 的任务；单任务还有条件状态更新作为领取保护。
- 终态按窄字段流式读取，均值保留每语种的和与数量；Corpus BLEU 累加 n-gram 充分统计量后统一应用平滑和长度惩罚，保持 SacreBLEU 语义。终态维护可重建查询摘要。
- 评价器参数拒绝布尔、字符串伪装的数字、分数型并发/重试次数、NaN/Inf 与越界值。BLEU floor 的 `smooth_value` 必须在 `(0, 1]`，避免此前大于 100 的评分。
- 评分落库统一校验有限数值、范围与单位；BLEU 对精确匹配产生的极小浮点超界做规范化。非法评分成为明确失败项，不保存成功 ScoreResult；原始响应也必须是有限值的合法 JSON。
- LLM `cache_policy=content_model` 保留原有同模型、跨 Prompt/修订缓存语义；`strict_revision` 额外匹配评价器修订、Prompt 和 endpoint。force 仍可跳过历史缓存，任务内部重复输入仍去重。
- 语种识别改为 SQL 分组计数，保留原 `accuracy`/`recall`，新增 `accuracy_on_covered`、`accuracy_overall`、逐语种 `coverage`/`recall_overall`，使缺失识别标签可计入总体分母。
- 完成后在独立短事务执行有界查询统计维护；维护失败记录日志，不改变已经提交的评分结果和完成状态。

## 自动化验证

```sh
.venv/bin/pytest backend/tests/test_worker_scalability.py backend/tests/test_import_and_queue.py backend/tests/test_audit_regressions.py backend/tests/test_logic_fixes.py backend/tests/test_evaluators.py -q
```

覆盖参数/分值有效性、流式 Corpus BLEU 与官方 `corpus_score` 一致、跨批次去重、严格与兼容缓存、无效历史评分跳过、运行状态、取消与重试、崩溃恢复、重复领取/重复 Worker、维护失败隔离和有界对象驻留。此前用 LLM 的 point/0–10 评分模拟 BLEU 的测试夹具已修正为与其评价器一致的量表，没有为测试放宽产品校验。

## 规模实测

每阶段是独立子进程，峰值 RSS 包含 Python/依赖基础占用。fixture 通过 Core 批量生成，不属于导入接口基准；40 个语种，源文/参考长度与审查时接近。

| 操作 | 24,000 条 | 400,000 条 |
|---|---:|---:|
| 建立一个评价器任务 | 0.33 s / 69 MiB | 5.18 s / 69 MiB |
| 首批装载 512 条 | 0.060 s / 68 MiB | 0.065 s / 68 MiB |
| 完整评分、落库和终态聚合 | 36.99 s / 119.5 MiB | 492.85 s / 90.5 MiB |
| 实际评价器 | 真实本地 SacreBLEU | 确定性本地 Judge |
| 完成 / 失败 | 24,000 / 0 | 400,000 / 0 |
| 全任务进度校准次数 | 2 | 2 |
| 最大单批行数 / ORM 实例 | 512 / 3,079 | 512 / 3,080 |

400,000 条场景真实执行了整个队列、持久化、进度和统计路径，产生 400,000 条 ScoreResult；评分输出由本地函数提供，**不代表真实 LLM 的吞吐或评分质量**，也没有声称实际跑完 40 万条 SacreBLEU。所有临时 fixture 与数据库已经清理。

旧实现建立 40 万任务项为 38.07 秒，初次全量装载约 23.48 秒 / 2 GiB；新实现初次只读取一个有界批次。没有运行旧实现完整 40 万条评分，因此不提供虚构的端到端加速倍数。

计时发生于并行开发中的本机，其他隔离探针可能同时使用 CPU/磁盘。**探针当时没有采集 SQLite `PRAGMA cache_size`，不能严格确认完整 Worker 子进程是否已经使用最终的 32 MiB 连接缓存配置。** 并行开发期间数据库配置统一为 `cache_size=-32768`；表中的 90.5 / 119.5 MiB 是对应测量进程当次记录的峰值，不能作为最终配置下相同绝对 RSS 的承诺。

收尾阶段还完善了查询摘要构建标记、有限 JSON 响应校验和可选短事务统计维护，并将非 BLEU 终态聚合改为不读取译文/参考全文的窄投影。这些收尾修改不计入上述耗时记录；未重复整个 40 万条耗时探针。规模结果用于确认该次完整队列成功、对象驻留受批次限制，以及消除逐项全量计数，不构成最终实现的服务吞吐或精确内存承诺。

证据：[规模测量 JSON](worker-scale-evidence.json)；复现：[worker_scale_probe.py](worker_scale_probe.py)。

当前仍以一个完整评价器任务作为 Worker 的外层调度单位；未引入跨任务公平调度、暂停恢复 API 或分布式多 Worker。
