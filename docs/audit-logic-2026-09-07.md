**新增缺陷 1 · P1：失败、取消后再重试，存在取消项的任务被标成 completed【运行复现】**

预期：重试只重新执行失败项，已取消项保留取消状态；存在取消项时，任务的最终状态和取消数量仍应反映这一事实。

复现使用 6 条标准演示预测，单并发模拟评价器，调用实际取消及重试逻辑：

1. 第 1 条失败，第 2 次请求等待该失败落库后取消父任务，最终为 1 条 failed、5 条 cancelled。
2. 调用 `/evaluator-jobs/{id}/retry-failed`，仅第 1 条再次评分并成功。
3. 数据库实际为 **1 条 completed、5 条 cancelled**，评价器与父任务状态却均为 **completed**。
4. 任务 API 报 `cancelled_items=0`；统计 API 报 `cancelled=5`、`coverage=1/6`，两者互相矛盾。

原因：[queue.py:690](../backend/app/queue.py#L690) 在重试结束时仅检查 queued 和 failed，没有根据取消项决定终态；重试已先把 job 改为 queued，因此此前 partial_cancelled 状态不能起保护作用。[api.py:166](../backend/app/api.py#L166) 又根据 job 状态决定是否计算取消数，使计数错误进一步传播至任务卡片。

建议：集中根据逐项终态计算任务终态；只有全部评分项成功才给出 completed。取消数应来自真实状态计数，避免通过总状态推断。父任务继续按子任务汇总即可。

验收：上述操作结束仍显示部分取消，成功 1、取消 5、总数 6；任务 API、统计 API 和逐句列表一致。

**新增缺陷 2 · P1：LLM 返回布尔值 score 会被写成有效评分【运行复现】**

预期：[README](../README.md#评分口径) 约定保存 0–10 数值评分；非数值类型不能被静默转换成成功分数。

模拟 HTTP 评分服务连续返回 `{"score": true}`，使用实际 LLM 客户端和队列执行 6 条预测：任务为 completed，6 条均成功，微平均为 **1.0**，没有任何失败。该值已通过正常评分持久化路径写入。

原因：[llm.py:213](../backend/app/evaluators/llm.py#L213) 直接调用 `float(data["score"])`，Python 会把 True 转为 1.0，后面的 0–10 范围判断继续通过。同理，False 会被解释为 0.0。

建议：在数值转换前拒绝 bool，明确允许的原始类型，再统一检查有限值和范围；对非法评分采用已有的可重试错误路径。修复时补 True/False、null、列表、对象、非有限值及正常整数/浮点数用例。

验收：布尔响应不能产生成功 ScoreResult，也不能进入后续历史缓存。

**新增缺陷 3 · P1：重试期间取消，BLEU 聚合可能继续使用旧样本集合【运行复现】**

预期：同一结果响应中的逐句成功集合、均值、corpus BLEU 及对应样本数必须一致；旧聚合不能被当成当前结果展示。

复现使用真实 SacreBLEU，仅通过评价器包装模拟部分请求失败与取消：

| 状态 | 成功样本 | corpus BLEU | 聚合记录样本数 |
| --- | --- | --- | --- |
| 首轮完成，4 成功、2 失败 | 4 | 53.025212 | 4 |
| 重试补成 5 成功，随后取消最后 1 条 | 5 | API 仍返回 53.025212 | 仍为 4 |
| 直接对当前 5 条成功样本重新计算 | 5 | **40.563199** | 5 |

同时，当前微平均为 49.962327，数据库保留的旧 sentence_mean 为 60.884245。这是样本集合变更后未更新聚合，区别于 sentence BLEU 均值和 corpus BLEU 本来就有算法差异。

原因：[queue.py:690](../backend/app/queue.py#L690) 对 cancelled/partial_cancelled 跳过 `_store_aggregates`；重试开始也没有失效旧聚合。[queries.py:146](../backend/app/queries.py#L146) 原样返回这些记录，[ResultsPage.tsx:128](../frontend/src/pages/ResultsPage.tsx#L128) 则显示为“全部 corpus BLEU”，没有展示对应的旧样本数。

另一个复现：首次 BLEU 评分成功 3 条后取消，逐句成功分数存在，但聚合记录数为 0。与 partial_failed 时生成成功子集聚合的行为不一致。

建议：成功集合改变时更新或失效聚合；所有终态统一处理当前成功样本集合。对于活动任务，可暂不提供 corpus BLEU，但需明确标示未生成，不能继续展示过期结果。若产品规定只对完整数据集生成 corpus BLEU，应统一所有非完整状态的策略。

验收：重试后取消的例子，若展示当前成功子集 corpus BLEU，应为 40.563199 且 sample_count=5；若不展示，应明确不可用，不返回旧值作为当前指标。

**新增缺陷 4 · P2：缺少有效评分的部分响应漏过重试分类【运行复现】**

在最大重试次数为 2 的评分包装中，让模拟服务第 1 次返回异常响应、第 2 次返回合法 9 分：

| 首次响应 | 实际调用数 | 实际结果 |
| --- | --- | --- |
| content 为非法 JSON 字符串 | 2 | 重试后成功得到 9 分 |
| score 为 11 | 2 | 重试后成功得到 9 分 |
| `choices=[]` | **1** | `未预期的评价器错误: list index out of range` |
| `content=null` | **1** | `未预期的评价器错误: 'NoneType' object has no attribute 'strip'` |

位置：[llm.py:211](../backend/app/evaluators/llm.py#L211)、[parse_json_content:109](../backend/app/evaluators/llm.py#L109)、[queue.py:348](../backend/app/queue.py#L348)。空数组触发 IndexError，空内容触发 AttributeError，均未进入当前响应解析的可重试错误分支。

建议：显式验证 choices、message 和 content 结构，统一处理缺少有效 score 的响应。对服务拒答等有明确含义的响应可分类为永久失败并说明原因；不要把缺少字段、空数组和空内容随机分到不同的“预期/未预期”错误路径。

验收：可重试的无效响应按配置重试；永久错误返回可读理由。该缺陷并不意味着所有 HTTP 4xx 都应重试，当前对认证等永久错误不重试的策略可以保留。

**新增缺陷 5 · P2：空白源语种核验通过，提交才报 500【运行复现】**

预期：严格导入应在核验阶段拒绝空字段，用户收到可操作的字段错误。

复现：清单 source_languages 中 code 为三个空格，样本 source_language 同样为三个空格。校验返回 valid=true，报告中的 languages 为 `[""]`；提交返回 500。进一步读取异常为 `DatasetManifest` 的 `source_languages.0.code` 长度校验失败。

原因：[schemas.py:10](../backend/app/schemas.py#L10) 和 [schemas.py:37](../backend/app/schemas.py#L37) 先执行 min_length 校验，再用默认的 after validator 做 strip/lower，合法长度的空格变成空字符串后没有再次验证。导入报告存储归一化后的空值；[importers.py:279](../backend/app/importers.py#L279) 提交时重建 schema 才拒绝，而 API 未将该异常转为导入错误。

建议：先规范化再校验，或在规范化函数内明确拒绝空值。校验和提交应共用同一规则；提交阶段的合法性复核错误也应返回明确 4xx。

验收：第一次核验即报告清单和样本的空语种，不能出现“核验通过 → 无说明的服务器错误”。

**独立验证正确的关键逻辑**

统计验证使用 7 条自建样本：de 成功分为 10、8、4；th 为 2 和 1 条失败；vi 的 2 条全部失败。阈值为 8，直接从输入算得：

| 指标 | 独立预期 | API 实际 |
| --- | --- | --- |
| 微平均 | (10+8+4+2)/4 = 6 | 6 |
| 宏平均 | ((10+8+4)/3 + 2)/2 = 4.666667 | 4.666667 |
| 微准确率 | 2/4 = 50% | 50% |
| 宏准确率 | (2/3 + 0/1)/2 = 33.333333% | 33.333333% |
| 覆盖率 | 4/7 = 57.142857% | 57.142857% |
| vi 展示 | 总数 2、失败 2、覆盖 0、均分缺失 | 一致 |

因此，当前成功评分子集的宏/微公式没有发现计算错误。第 3 项是持久化聚合过期，不应混同为所有统计公式都有问题。

中断恢复验证实际启动评分协程，在 3 条已落库、3 条未完成时中断，再调用恢复逻辑并执行。恢复后 6/6 完成，新增评分调用为 3，已提交的 3 条没有重复调用。这验证了已提交进度的保留；不保证崩溃前已发出但尚未提交的外部请求不会在恢复时再次执行。

另外重新运行 8 个既有参数化场景，全部通过：提交原子性/幂等性、实际来源比较、缓存与强制重评、预测暂存修改复核、父任务/数据集取消停止待发送请求。前一轮全量 36 项测试和前端构建也已通过；本次没有代码修改，未重复前端构建。

**属于既定口径或尚需明确的产品语义**

- 更换 Prompt/Base URL 仍可命中历史缓存，是 README 明确约定。要验证新 Prompt 的真实效果，应强制重评；界面的提示不足见前一轮报告。
- 已有任务继续绑定旧评价器修订，是界面明确的历史快照策略。缺少基于旧提交创建新配置任务的入口，是维护工作流缺口；不能通过静默修改历史任务来“修复”。
- 当前宏统计不把全部失败的语种当作 0 分，而是排除其均值、保留覆盖信息。当前语种识别 accuracy 则按已有预测语种的样本计算。本次 7 条中仅 4 条提供语种且全部正确，accuracy=100%、coverage=57.14%，符合既有测试口径；如业务预期按全部样本衡量成功率，应明确增加相应指标。
- 强制重评绕过历史缓存；当前执行过程中，相同文本键仍会进行组内复用。若业务要求每个重复样本独立采样一次，需要另行明确此语义，不宜仅凭“强制”二字推断。
