**TranslateEval：多数据集、多版本、30–40 语种的规模适用性评价**

评价日期：2026-09-07。基于当前工作区，包括已完成的 TranslateEval / ARI-NLP 品牌修改；本次没有修改业务代码。用户给定条件为多个数据集、每集多个版本，每个版本 30–40 个语种、每个语种 600–10,000 条。

**结论**

领域模型与大部分页面可以继续沿用，但当前实现不适合原样作为上述完整规模的长期系统。每版本约 2 万条时，基础导入和单次查看已有可用性能；接近 40 万条时，长事务、全量 ORM 装载、逐项进度重算和重型比较已经有实测瓶颈。多个版本和多轮评测会进一步放大存储、查询及调度成本。

40 个语种的普通表格展示本身可用：当前各语种结果每页 10 条，逐句明细每页 50 条，样本预览每页 20 条。没有把 40 万行全部送到浏览器。需要重点调整的页面是多数据集查找、长版本历史、多数据集任务卡和跨模型的语种对比，而不是重新设计所有页面。

| 范围 | 当前适用性 |
| --- | --- |
| 少量数据集、每版本 1.8–2.4 万条、少量历史实验 | 基础导入/查看可用；此前发现的可靠性问题仍需修复，完整大任务评分未在本次跑完 |
| 每版本 30–40 万条，单轮评测 | 数据能够入库，但导入、Worker 内存与进度维护已经需要优化，不宜用当前交互和执行机制直接长期运行 |
| 多数据集 × 多版本 × 多轮 × 多评价器 | 需要汇总查询、分块调度、容量管理与页面检索能力；当前实现尚未通过这一累计规模验收 |

**规模应如何计算**

| 语种数 | 每语种样本数 | 单个数据集版本的总样本 |
| ---: | ---: | ---: |
| 30 | 600 | 18,000 |
| 40 | 600 | 24,000 |
| 30 | 10,000 | 300,000 |
| 40 | 10,000 | 400,000 |

当前每个版本完整保存样本；每次新导入的推理运行保存一套预测；每个评价器任务保存一套 EvaluationItem。使用“再次评测”会复用原预测，但仍新增任务项与必要的新评分。缓存能减少新评分和模型调用，不能消除任务项。

一个仅用于容量规划的例子：**5 个数据集 × 5 个版本 × 每版本 40 万条**，已有 **1,000 万条样本记录**。如果每个版本各导入 10 轮不同模型预测，就有 **1 亿条预测**；每轮选 2 个评价器，则有 **2 亿条评价任务项**，另加未被缓存复用的评分记录和原始响应。这些数据集/版本/轮次数是假设，不是用户已经承诺的数量，也没有在本次全部造出。

每语种 600 和 10,000 的比例相差 16.7 倍。当前按样本加权的指标会赋予大语种更高权重，宏平均则按语种等权；二者都应保留。跨多个数据集进一步汇总时，需要明确按句子、按语种还是按数据集加权，并固定所比较的版本组合，不能把不同数据版本的结果直接混成一个总分。

**实际测到的导入与执行准备成本**

使用 40 个语种，每语种分别 600 / 10,000 条；第二版本仅修改约 1% 的参考译文。每个阶段使用独立子进程，下面内存为该子进程峰值 RSS，包含 Python/库的基础占用，不是纯业务对象大小。源文平均约 163 字节，参考译文约 195 字节；长句、长推理输出和长评分理由会增加占用。

| 实际业务 helper | 2.4 万条 | 40 万条 | 40 万条进程峰值 |
| --- | ---: | ---: | ---: |
| 数据集核验 | 0.52 秒 | 8.13 秒 | 563 MiB |
| 数据集提交 | 3.16 秒 | 59.69 秒 | 625 MiB |
| 新版本差异核验 | 1.11 秒 | 19.30 秒 | 1,484 MiB |
| 新版本提交 | 3.22 秒 | 61.83 秒 | 626 MiB |
| 预测核验 | 0.41 秒 | 6.91 秒 | 750 MiB |
| 预测提交 | 2.79 秒 | 57.27 秒 | 673 MiB |
| 建立单评价器任务项 | 2.11 秒 | 38.07 秒 | 149 MiB |
| Worker 全量装载待评项 | 1.47 秒 | 23.48 秒 | 约 2 GiB，仅预处理 |

这不是完整 HTTP 上传耗时。当前可编辑导入的 prepare 还会读一遍文件；提交评测 API 又把“预测提交”和“建立任务项”放在同一事务中，实际一次提交的工作包含这两个阶段。不能把表里某一项当作从浏览器点击到完成的总时间。

40 万条提交虽然每 1,000 条 flush，实测仍发出约 40 万次 SQL 插入，并在整个提交结束时才 commit。第二版本提交的约 62 秒期间，另一个隔离数据库连接按当前 30 秒超时尝试取得写锁，**30.19 秒后返回 `database is locked`**。该探针仅尝试开启写事务，若成功则回滚；本次超时，未写入或提交任何修改。它证明写锁竞争，未逐个测试所有取消/提交 API 的错误返回。

Worker 全量装载时有约 **120 万个 ORM 实例**驻留。之后缓存字典、`current_results` 和终态聚合还会保留或重新读取评分对象，因此 2 GiB 只是本次装载路径的占用，不能当作整个评测的内存上限。

本次两个 40 万条版本、一次预测、一个尚未执行的评价器任务，数据库约 **1.015 GB**，暂存原文件另约 **470 MB**，还没有任何实际 ScoreResult。这个体积依赖文本长度和夹具内容，不能当作任意语料的固定每行开销；它说明版本与任务项即使没有模型响应也会累积占用。

40 万条任务上，一次 `_refresh_progress` 加提交的暖态测量约 **0.28–0.29 秒**。当前每个独立评分组都调用一次，并两次扫描此任务的明细；若 N 个样本互不重复，累计计数工作量随 N² 增长。没有实际执行 40 万轮评分，也不能把这次计数耗时简单宣称为完整任务的实测耗时。这个算法成本本身已经足以要求修改。

证据：[导入与 Worker 测量](scale-review-2026-09-07/import-worker-evidence.json)、[并发写锁测量](scale-review-2026-09-07/import-concurrent-writer-evidence.json)。代码：[导入全量解析及提交](../backend/app/importers.py#L109)、[任务项创建](../backend/app/queue.py#L48)、[待评项全量装载](../backend/app/queue.py#L244)、[进度计数](../backend/app/queue.py#L384)、[终态聚合](../backend/app/queue.py#L447)。

**缓存与查询需要按大库维护**

独立缓存探针向库中写入同一模型的 24,000 / 400,000 条合成历史评分，使用实际 `_preload_llm_cache` 查询 200 个内容键。没有执行任何 LLM 请求。

| 缓存条件 | 200 键命中耗时 | 查询计划观察 |
| --- | ---: | --- |
| 2.4 万条历史，未建立统计 | 约 0.023–0.026 秒 | 主要按 evaluator_type 索引筛选，再做内容键匹配 |
| 40 万条历史，未建立统计 | 约 0.278–0.340 秒 | 同样未充分利用内容复合索引 |
| 同一 40 万条库执行 ANALYZE 后 | 0.0087 秒 | 改用模型、语种、源文哈希复合索引前缀 |

这说明现有复合索引并非没有价值，统计维护与查询形状对大库至关重要。40 万个不同输入会分成 2,000 批缓存查询，因此不应只看单批耗时；也不能把这里的单批耗时乘 2,000 就称为完成整轮的实测结果。后续应验证真实模型数、Prompt 历史深度和命中率下的计划，并尽量在 SQL 中选出每个键的最新有效评分。

证据：[缓存测量与 ANALYZE 前后计划](scale-review-2026-09-07/cache-evidence.json)。

当前结果查询有两种不同情况：普通 summary 和明细使用 SQL 聚合/分页，Python 内存基本有界；严格比较则会把所选任务的全部 ScoreResult ORM 读入 Python。结果列表默认只汇总当前页的任务，但按平均分/准确率排序会先聚合全部匹配任务，再分页。每页只显示 20 行不能限制这种排序的后端工作量。

另一组独立 API 夹具通过 Core 批量写入，分别创建每版本 2.4 万 / 40 万条的两个版本，以及两个完整模型结果；没有通过导入接口造数，也没有真实模型评分。API 计时含 TestClient 请求和序列化，不含造数和进程启动。40 万条组共 80 万样本、80 万预测和 80 万评分，SQLite 约 2.62 GiB；每个查询用独立子进程，普通查询峰值约 79 MiB。

| API 操作 | 每任务 2.4 万条 | 每任务 40 万条 |
| --- | ---: | ---: |
| 结果汇总 summary | 约 0.20 秒 | 2.67 秒 |
| 逐句评分首屏 50 条 | 约 0.24 秒 | 3.94 秒 |
| 逐句评分最后一页 | 约 0.68 秒 | 11.07 秒 |
| 逐句分数排序首屏 | 约 0.28 秒 | 4.44 秒 |
| 先限定一个语种 | 约 0.10 秒 | 0.19 秒（单语种 10,000 条） |
| 精确样本 ID 查询 | 约 0.08 秒 | 0.08 秒 |
| 结果列表，仅 2 个结果 | 0.34 秒 | 5.39 秒 |
| 结果列表仅返回 1 个结果 | 0.23 秒 | 2.69 秒 |
| 按均分排序，仅返回 1 个结果 | 0.47 秒 | 7.70 秒（仍有 2 个候选结果参与聚合） |
| 比较 2 个结果 | 2.43 秒 | 40.82 秒；峰值 RSS 2,492 MiB |

比较响应只有约 13.6 KB，但内部读取和对象构造十分昂贵。ANALYZE 后复测，40 万条首屏仍约 3.95 秒、末页约 10.92 秒、比较约 40.51 秒和 2,492 MiB 峰值；说明缓存案例的统计维护收益不能套用到全部接口。

把同一大库增加到 **6 个完整历史任务**后，共有 240 万条 EvaluationItem、80 万条可共享的 ScoreResult，并再次执行 ANALYZE。结果列表返回其中 1 条约 3.20 秒，默认返回 6 条约 **18.25 秒**；按均分排序即使只返回 1 条也需 **20.67 秒**。SQL 语句数仍然只有 14 次。查询次数被控制住了，每条查询内部扫描的样本量仍会增长，列表需要已保存的摘要而非每次扫描任务原始明细。

查询计划还确认默认排序存在额外临时排序：通用 `table_order` 给非空 ID 也加了 `IS NULL` 排序表达式，首屏分页因此不能充分利用自然索引顺序。后续应针对可空分数保留“空值在最后”，对已知非空主键避免无意义表达式，并验证组合筛选后的计划。按语种和精确 ID 已经很快，应保留这些入口。

证据：[API 专项分析](scale-review-2026-09-07/query-findings.md)、[API 基准脚本](scale-review-2026-09-07/benchmark_queries.py)、[2.4 万条查询记录](scale-review-2026-09-07/query-results-24000.jsonl)、[40 万条查询记录](scale-review-2026-09-07/query-results-400000.jsonl)、[更新统计后](scale-review-2026-09-07/query-results-400000-analyzed.jsonl)、[6 个历史任务](scale-review-2026-09-07/query-results-400000-history6-analyzed.jsonl)。

实时刷新也要考虑成本：当前 SSE 每秒检查全局任务变化；打开的活动详情会刷新上下文、汇总和明细，其他任务的变化也能触发它。前端已有请求合并，不会同一 hook 无限重叠请求，这是正确的；但一个耗时数秒的查询仍可能结束后立即再查。在大任务运行时，需要按相关 job 推送增量和节流，避免页面持续要求全量重算。

**按页面看，哪些保留、哪些应调整**

浏览器使用模拟 API 验证布局和操作，样本 total 设置为 400,000。额外假设为 12/20 个数据集、20 个版本，以及 20 个任务每个包含 12 个数据集和 2 个评价器；这些数量仅用于观察增长趋势，不能当成后端真实负载测试。

**评测范围、调度与版本策略**

目前预测必须完整覆盖绑定版本的全部样本；任务单元是“整个数据集版本 × 一个评价器”，语种只是内容和统计维度。没有只提交某几个语种、只评抽样集、追加一部分预测或按语种调度的正式范围模型。这个严格性保护了原有统计，但完整版本达到 40 万句后，会限制日常试验。

建议新增不可变的“评测范围快照”：绑定数据集版本并持久化实际入选的精确样本集合，记录入选语种和样本数；抽样种子、算法及其版本作为追溯信息，不能仅凭种子代表范围。在该范围内保持预测完整性。未入选样本与评分失败必须区分；通过率的分母、缓存来源与严格比较都引用同一个范围。多数据集实验还应固定一组版本清单与汇总权重，避免不同轮次意外混用各自的最新版。

执行层可保留现有父任务结构，在内部按语种/固定大小拆分工作批次，使长任务可以检查点恢复、公平轮转和隔离失败。添加多个 Worker 前必须先处理上一轮发现的原子领取与归属问题。不要通过直接重复启动当前 Worker 来增加并发。

外部评分时间也需要纳入交互。以每条请求平均 5 秒、没有命中缓存、不重试、服务不限流为假设，仅计算 `样本数 × 5 / 并发数`：

| 单评价器任务 | 并发 8 | 并发 32 |
| --- | ---: | ---: |
| 24,000 条 | 4.17 小时 | 1.04 小时 |
| 400,000 条 | 69.44 小时 | 17.36 小时 |

这些是理想化服务时间估计，不是实测速度，也没有包括本次已发现的数据库开销。当前 Worker 会顺序执行整个评价器任务，长 LLM 任务会让后续短 BLEU 任务等待；进度、队列公平性、范围选择和恢复能力应按小时至天的任务设计。

不可变版本可以继续保留。先补容量统计、暂存生命周期和归档，再依据版本间实际重复率决定是否把正文按内容哈希复用、版本仅记录成员映射。没有必要仅因为有 40 个语种就引入复杂增量版本存储。

**数据库选择与建议实施次序**

SQLite 可以存放大数据文件，40 万行并非它的硬上限；但 WAL 仍然只有一个写者，本次长导入与另一个写事务的冲突已经复现。对于持续多数据集导入、后台评分和多人查看/操作的目标，建议将 PostgreSQL 作为长期主库方向，SQLite 保留为本机轻量模式。迁移数据库仍需同步解决全量加载、计数算法和比较查询。[SQLite 官方 WAL 并发说明](https://sqlite.org/wal.html#concurrency)、[官方适用场景](https://sqlite.org/whentouse.html)

| 顺序 | 具体工作 | 保留的正确设计 |
| --- | --- | --- |
| 1：大任务执行与写入 | 流式解析/校验，真正批量写入；后台导入；内部短事务配合 staging 状态，最后原子发布版本/提交；分批装载/落库、增量计数、有限缓存驻留、可合并的终态统计 | 不可变版本、严格完整性、逐句原始分、历史配置快照 |
| 2：常用查询与比较 | 明确索引与统计维护；修正影响索引排序的表达式；维护按任务/语种摘要；严格比较用 SQL 检查样本/来源差异，避免装载全部原始响应；推送相关任务并节流 | 服务端组合筛选、精确 ID、URL 状态、评分来源追溯 |
| 3：实验与页面规模 | 评测范围快照、按语种抽样、版本清单、分块公平调度；数据集/版本检索、任务折叠、模型语种矩阵与导出 | 数据集 → 提交 → 队列 → 结果的页面分工 |
| 4：长期容量与部署 | 主库迁移验证、暂存回收、归档/备份、容量监测、跨版本正文复用的收益评估 | 模块化单体，无需因此拆成微服务 |

后台导入与短事务需要明确“未发布”的中间状态，不能简单把当前一个大事务拆成多次 commit 后就把半成品暴露为已完成版本。流式 ORM 读取同样要求全链路不再 `.all()` 或把已处理对象持续放进全局字典；SQLAlchemy 官方文档明确说明 yield_per 的适用方式及一次性取全量会抵消分批读取的作用。[SQLAlchemy 查询文档](https://docs.sqlalchemy.org/en/20/orm/queryguide/api.html#fetching-large-result-sets-with-yield-per)

建议下一轮把验收目标明确为：40 语种 × 10,000 句的真实导入/完整评分/取消恢复；多个版本和多轮结果累计；后台评分期间至少数个浏览器同时查询。可先约定常用筛选/首屏 p95 小于 1–2 秒、重型比较后台化或数秒内返回、Worker 内存由批次和并发决定、未发出的评分在取消后数秒内停止调度。这里是建议目标，目前没有声称已经达到。

**验证边界与证据**

所有测试使用独立临时 SQLite、合成文本和模拟浏览器数据，没有触碰实际业务数据库、没有真实 LLM 调用、没有运行 40 万条逐项评分。导入、SQL 查询和浏览器布局是三组不同验证，不能混为同一端到端负载测试。后端阶段有子进程隔离；计时在本机进行，其他隔离探针也可能同时占用 CPU/磁盘，OS 页缓存没有清空。结果用于定位设计瓶颈，不是硬件容量承诺。

现有 172 项测试和此前正常流程结果仍有效；它们不覆盖这次新增的长期容量目标。本次针对规模增加探针，没有修改业务代码或重新重复整套小数据测试。证据与重跑说明见 [规模验证目录](scale-review-2026-09-07/README.md)。
