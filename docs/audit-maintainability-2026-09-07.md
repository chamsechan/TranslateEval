**1. P1：编辑评价器会静默覆盖没有展示在表单中的参数【浏览器复现】**

位置：[SettingsPage.tsx:56](../frontend/src/pages/SettingsPage.tsx#L56)、[保存配置:68](../frontend/src/pages/SettingsPage.tsx#L68)。

通过 API 创建合法配置，再在界面操作：

| 操作 | 保存前 | 保存后 |
| --- | --- | --- |
| LLM 只改并发数 1 → 2 | `temperature=0.7`、`max_tokens=1024` | `temperature=0`、`max_tokens=256` |
| BLEU 打开编辑后直接保存 | `smooth_value=0.5`、`effective_order=false` | `smooth_value=null`、`effective_order=true` |

原因是表单没有承载这些参数，保存时重新拼接配置并写入硬编码默认值。后端支持的配置与界面可维护的配置不一致。问题主要影响经 API 设置的非默认参数；完全由当前界面创建且一直使用默认参数时不一定显现。

这会改变后续任务的评分请求或 BLEU 计算行为，用户却只操作了并发或直接保存。建议编辑时保留原有完整配置，仅覆盖实际可编辑字段；对被后端支持且影响评分的参数提供高级字段。未修改内容时避免产生无意义修订。

验收：只修改并发数，其他配置逐项保持不变；BLEU 原样保存保留平滑值和 effective_order；新增配置仍采用明确默认值。

**2. P2：服务配置修复后，失败任务缺少使用新修订恢复的入口【运行复现／工作流缺口】**

位置：[retry_failed_job:197](../backend/app/queue.py#L197)、[创建评价器实例:593](../backend/app/queue.py#L593)、[新增配置修订:823](../backend/app/api.py#L823)。

复现：r1 的模拟凭证已失效，6 条评分失败；随后将同一评分配置更新为有效凭证 r2，点击原任务的“重试失败项”。重试产生的 6 次请求仍全部使用 r1，任务再次失败。以 r2 创建新任务则可成功完成。

保留旧任务配置是界面明示的设计，也是历史可复现性的保障。维护缺口在于：用户修复服务以后，界面没有“使用新修订重新评测”的配套路径，只能继续重试旧配置或重新导入文件。

建议增加“基于原推理提交，使用所选修订创建新任务”，保留原任务及其来源。对于实际出现频繁密钥轮换的场景，再考虑将凭证引用与影响评分的配置版本分开；不必先建设独立凭证管理服务。

验收：失效凭证导致失败后，可从任务页选择有效配置完成新一轮评分，同时可追溯旧任务与新任务的关系。

**3. P2：已有推理结果难以直接复用，模型记录的维护价值受限【运行复现／代码确认】**

位置：[模型列表:18](../frontend/src/pages/ModelsPage.tsx#L18)、[模型响应:928](../backend/app/api.py#L928)、[提交幂等处理:420](../backend/app/api.py#L420)、[新建运行记录:499](../backend/app/importers.py#L499)。

模型记录页面可以搜索、分页，但没有运行详情、关联结果跳转、备注维护或再次评测操作。数据库已保存完整 `result_info`，列表响应及结果上下文却没有提供 decoding、precision、code_revision 等完整复现参数。

底层 `create_evaluation_task` 支持复用同一个 `InferenceSubmission`。目前公开 API 只通过“导入核验记录 → 提交”调用它。实测对同一个核验记录改用另一个评价器再次 commit，仍返回原任务；这是正确的幂等行为，但没有相应的“新建评测”接口。用户重新核验同一结果目录，又会生成新的 ModelRun、Submission 和预测记录。

建议补运行详情和基于已有提交创建新评测的 API/页面入口。备注或标签如需编辑，应与不可变推理参数区分。该需求可以沿用现有表和创建任务函数，无须先引入新的模型注册平台。

验收：同一批预测更换评分模型、Prompt 或强制重评时，无须再次上传；页面可查看本次运行的完整复现参数与关联结果。

**4. P2：评价器注册表尚未成为完整扩展边界【运行复现／代码确认】**

已有 [BaseEvaluator](../backend/app/evaluators/base.py#L38)、`ScoreInput`/`ScoreOutput` 与 [静态注册表](../backend/app/evaluators/registry.py#L10)，方向合理。实测在进程内注册一个实现接口的新评价器后，注册表配置校验通过，但创建配置 API 返回 **422 / literal_error**，因为 [请求模型:142](../backend/app/schemas.py#L142) 只允许两个内置类型。

扩展影响还会继续向外传播：

| 规则 | 当前散落位置 | 新增类型的影响 |
| --- | --- | --- |
| 支持的类型及表单 | `schemas.py:142`、`types.ts:80`、`SettingsPage.tsx:126` | 注册后仍须同步修改前后端枚举和界面 |
| 是否需要 Prompt、如何构造实例 | `registry.py:36`、`queue.py:66`、`SubmitPage.tsx:54` | 根据具体类或类型字符串判断，其他需要 Prompt 的实现无法直接复用 |
| 分值范围、单位 | `validation.py:22`、`queries.py:153`、`ResultsPage.tsx:79` | 除 BLEU 外一律按 0–10 处理，未统一使用评价器声明的尺度 |
| 语料级聚合 | `queue.py:481`、`queue.py:514`、`ResultsPage.tsx:128` | 通用接口已有 `corpus_aggregates`，执行与展示却只认 BLEU |
| 历史缓存 | `queue.py:308`、`queue.py:606` | 明确限定当前 LLM 类型；新增实现需要选择并落实缓存策略 |

这并不意味着新增算法必须完全不写界面；问题在于调度、查询与校验重复维护同一类能力规则。建议先给注册项集中声明分值范围、单位、是否需要 Prompt、构造函数等少量真实需要的信息，令阈值和汇总读取同一个来源。语料级指标按评价器返回值存储与展示。表单仍可保持显式实现。

新增评分模型还必须满足当前适配器的固定请求形状：[llm.py:186](../backend/app/evaluators/llm.py#L186) 固定调用 `chat/completions`，传入 system 消息、temperature、max_tokens、JSON response_format，并解析 0–10 分。不能把填写 Base URL 理解成支持任意模型服务。当前 `/models` 检测已经明确提示“实际评分尚未试跑”，建议补一条样本评分试跑，以覆盖真实请求兼容性。

验收：接入第三种评价器时，调度与统计不需要再新增按类型名称判断的分支；新类型的阈值、单位与结果展示正确。

**5. P2：Prompt 容易录入，但新 Prompt 实验的反馈不够直接【运行复现／界面流程确认】**

位置：[Prompt 界面:78](../frontend/src/pages/SettingsPage.tsx#L78)、[选择版本:99](../frontend/src/pages/SubmitPage.tsx#L99)、[缓存开关:110](../frontend/src/pages/SubmitPage.tsx#L110)。

已具备四个变量校验、版本历史、复制最新版本及发布/草稿状态，应予保留。当前工作流仍存在以下限制：

- 表单没有基于真实样本的渲染预览和评分试跑，合法模板仍可能包含不合适的评分说明。
- 每个评价器修订在提交页只有一个 Prompt 选择框。同一评分模型比较多个 Prompt，需要分次导入或复制评价器配置；底层任务选择本身已允许不同的 revision/Prompt 组合。
- 历史版本卡片没有逐版本的复制操作；“复制为新版本”固定取最新版本。草稿没有原版本编辑或发布入口，需再次复制创建新版本。
- 实测同一模型已用 Prompt A 评分，换成 Prompt B、不开启强制重评时，6/6 条来自缓存，实际新模型调用数为 0。

最后一项符合 README 约定的宽松缓存口径，**不是缓存实现错误**。当前界面没有在选择新 Prompt 的位置明确说明“可能完全不执行本次 Prompt”。结果比较已有实际来源检查，不能将旧报告中“缓存误标严格可比”的问题重复归到当前代码。

建议给 Prompt 变更场景增加就地缓存说明或明确的“重新执行本次 Prompt”操作；结合第 3 项补已有结果再次评测，增加样本预览和逐版本复制即可显著降低实验成本。

**6. P2：数据接入的最后一段仍依赖手工文件操作，旧版本重复导入校验不完整【浏览器／运行复现】**

位置：[数据集界面:78](../frontend/src/pages/DatasetsPage.tsx#L78)、[版本历史:94](../frontend/src/pages/DatasetsPage.tsx#L94)、[导入版本查重:192](../backend/app/importers.py#L192)。

统一清单和 JSONL、严格核验、内容哈希、自动登记新源语种，足以支持标准协议内的数据扩展。当前页面没有可下载的模板、字段映射、样本预览或版本差异正文；导入摘要和错误仍大量直接展示英文键名与 JSON。后端已有 [样本分页查询:349](../backend/app/api.py#L349)，可直接补前端入口。

另有可复现的校验问题：导入 v1，再导入内容不同的 v2，随后重新核验原始 v1。界面对应的核验结果为 valid=true，提交才收到 400，响应包含数据库 UNIQUE constraint 错误。校验阶段只比较最新版本，数据库唯一约束覆盖全部历史版本，因此前后口径不一致；最终写入被正确阻止，没有写出重复版本。

建议查重覆盖该数据集的所有历史标签和内容哈希，并返回已存在版本的明确提示。优先补模板下载、样本预览、完整哈希复制和推理结果清单生成。若常用数据确实来自 CSV 等格式，再增加薄转换层，将其统一转为当前协议。

验收：历史重复在核验阶段直接说明；用户从界面核查样本、复制版本哈希并获得可用结果模板。

**7. 高内聚、低耦合的进一步判断【设计审计】**

应保留的结构包括：数据集与版本、推理提交与预测、Prompt 与版本、评价器与修订、评分结果与任务分离。这些实体分别服务于版本追溯、再次评分与缓存来源，并非仅为抽象而抽象。任务/数据集/评价器三级也对应多数据集、多评价器和分级取消需求，当前没有证据表明应该合并。

当前职责集中在两个文件：`api.py` 959 行，承担领域路由、业务事务、列表查询、序列化和实时通知；`queue.py` 805 行，承担任务创建、状态变化、执行、缓存、评分聚合及语种识别统计。文件长度本身不构成缺陷，但第 2—4 项显示了真实影响：已有提交重用没有公开操作入口，评价器能力又需要跨多层同步维护。

另一个具体依赖问题是：`threshold_summary` 已迁入 `queries.py`，API 仍通过 [queue 的导入项](../backend/app/api.py#L49) 获取它，统计查询仍在依赖任务执行模块的导出。前端通用 `useApiQuery`、`useTaskChanges` 以及统一错误展示已有价值；后端响应多为手写字典，前端再维护对应类型，构建通过不能保证两侧契约完全一致。

建议随下一次功能修改做小范围调整：按数据集、设置、任务/结果拆路由；让统计直接依赖 queries；把创建/再次评测等业务操作暴露为明确函数；将任务状态变化与评分执行分开。优先解决本报告中的改动传播问题，避免按固定行数机械拆文件。

**8. “没有过度设计”的判断及维护边界【设计审计】**

在当前单机定位下，SQLite、FastAPI/React、独立 Worker、持久化任务和静态评价器注册表规模适当。不可变历史、缓存实际来源、取消与恢复都是已存在的业务需求，相关复杂度具有理由。主要问题是一些规则分散、部分工作流没有接到界面，增加一般化抽象层并不能自动解决。

运维方面还有两个应明确的边界：

- `worker_loop` 先查 queued 任务再执行；Worker 启动时会重置所有 running/preprocessing 任务，缺少按 Worker 归属恢复的机制。当前应按单 Worker 使用，并优先增加防止重复启动的简单保护；不能通过直接多开 Worker 获得可靠并行。
- 导入会复制或解压到暂存目录；当前只有解压/复制异常时清理，成功提交、核验失败及放弃的展开目录缺少保留期限与清理入口。长期使用需要一个简单清理命令和明确保留规则。

上述边界不要求立即引入分布式队列、微服务、动态插件发现、通用表单引擎或多层仓储。保留现有架构，用少量明确的能力声明、业务函数和维护入口即可推进。
